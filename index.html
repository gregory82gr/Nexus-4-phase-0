The processor

An RV32I, multi-cycle, in-order RISC-V core in VHDL, with scratchpad memory and no caches, so its timing can be bounded. It is built in two fault-tolerance profiles: PLANT (NEXUS-1) and ORBIT (NEXUS-2).

The guardian

A small, hardwired unit derived from a formal specification. It watches the processor and steps in when a safety, bounded-liveness or idempotency property is violated, whatever the cause.

Why NEXUS-4

the series

NEXUS-3 was about hiding time: out-of-order cores, caches and latency tolerance. NEXUS-4 is about the opposite: making time predictable and making a processor checkable.

Its processor is meant for the first two NEXUS systems: the protection channel of the NEXUS-1 plant (fail-safe) and the on-board computer of a NEXUS-2 satellite (fail-operational).

No component is trusted without an independent oracle. See Verification.

Scope note
NEXUS-4 is a demonstration and study tool. Its processor has not been synthesized for, or qualified on, any real device. It is not certified to any safety standard and must not be used to protect any real plant, vehicle or person. Standards are cited for orientation only.
What this is
The NEXUS-4 simulation kernel, running in your browser. The examples are the same files that CI runs through GHDL on every push, and the kernel agrees with GHDL on every delta cycle of each one. Once you edit an example, nobody checks your version: the kernel runs it, reports a VHDL error with its line, or says which construct it does not support yet.
What this is
The NEXUS-4 assembler for the RV32I base instruction set, with the pseudo-instructions of the GNU assembler expanded the way GNU expands them. Code starts at 0x00000000 and data at 0x00010000. On every push, CI assembles the sample programs and a few thousand random instructions with both this assembler and GNU binutils, and fails unless the bytes and the symbol addresses are identical. The listing on the right is printed by the NEXUS-4 disassembler, which is checked against objdump the same way. Click an instruction to see its bit fields.

How the oracle works
differential testing

          

            
GHDL runs each example with --trace-signals. After every simulation cycle it prints every scalar signal with its value and two flags: A (active: a driver was updated) and E (event: the value changed). Composite signals appear as their scalar parts, for example m(1)(0) or r.n.

            
The NEXUS-4 kernel produces the same snapshots. The test tools load the kernel straight out of this file, with no build step, and any difference in a cycle, a value, a flag or a message fails the build. An example that uses a construct the kernel does not support yet is reported as pending; an example marked as required may never be pending.

            
One calibrated exception: for an assignment with a single zero-delay element that gives a signal the value its driver already has, with nothing else pending, the language standard still records a transaction. Nothing in the NEXUS-4 subset can observe it, so GHDL leaves it out. The kernel keeps it and tags it, because the difference between a transaction and an event is a lesson of the course, and the comparison leaves out exactly the tagged ones.

            
The tests are themselves tested: tools/mutations.mjs breaks the kernel in specific ways (inertial delay, resolution, rising_edge, delta counting and more), and every broken copy must fail.

            
VCD waveforms are only a secondary check: VCD merges the delta cycles of a time step, cannot hold arrays of vectors, and may reduce std_logic to four states.

About
NEXUS series

          

            
NEXUS-4 is the fourth system in the NEXUS series, after NEXUS-1 (nuclear plant), NEXUS-2 (satellite constellation) and NEXUS-3 (shared-memory multiprocessor).
