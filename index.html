The processor

An RV32I, multi-cycle, in-order RISC-V core in VHDL, with scratchpad memory and no caches, so its timing can be bounded. It is built in two fault-tolerance profiles: PLANT (NEXUS-1) and ORBIT (NEXUS-2).

The guardian

A small, hardwired unit derived from a formal specification. It watches the processor and steps in when a safety, bounded-liveness or idempotency property is violated, whatever the cause.

Why NEXUS-4

the series

NEXUS-3 was about hiding time: out-of-order cores, caches and latency tolerance. NEXUS-4 is about the opposite: making time predictable and making a processor checkable.

Its processor is meant for the first two NEXUS systems: the protection channel of the NEXUS-1 plant (fail-safe) and the on-board computer of a NEXUS-2 satellite (fail-operational).

No component is trusted without an independent oracle. See Verification.

Scope note
NEXUS-4 is a demonstration and study tool. Its processor has not been synthesized for, or qualified on, any real device. It is not certified to any safety standard and must not be used to protect any real plant, vehicle or person. Standards are cited for orientation only.
What this is
The NEXUS-4 simulation kernel, running in your browser. The examples are the same files that CI runs through GHDL on every push, and the kernel agrees with GHDL on every delta cycle of each one. Once you edit an example, nobody checks your version: the kernel runs it, reports a VHDL error with its line, or says which construct it does not support yet.
What this is
The NEXUS-4 assembler for the RV32I base instruction set, with the pseudo-instructions of the GNU assembler expanded the way GNU expands them. Code starts at 0x00000000 and data at 0x00010000. On every push, CI assembles the sample programs and a few thousand random instructions with both this assembler and GNU binutils, and fails unless the bytes and the symbol addresses are identical. The listing on the right is printed by the NEXUS-4 disassembler, which is checked against objdump the same way. Click an instruction to see its bit fields. Then run the program, one instruction at a time or to its end, on the NEXUS-4 ISA reference model: the specification the processor is held to, itself compared with Spike, the RISC-V reference simulator, on every push. And run it on the processor itself, the multi-cycle core in VHDL, simulated in this page by the kernel of the course and compared with the model on every instruction and every cycle.

What this is

        The multi-cycle RV32I core of rtl/, simulated in this page by the kernel of the course, and shown one clock cycle at a time. Everything drawn here comes from the signals of that simulation: the state of the control state machine, the values on the datapath, the register file, the commits. Nothing is computed by a second model of the core, so what you see is what the VHDL does. The kernel reports these signals through watched signals, which CI checks against its full snapshots on every course example, and the snapshots against GHDL. The column ✓ compares each commit with the ISA reference model. Upset flips one bit of the running core (a single-event upset, kept until the bit is written again) and says what it did to the program: masked, late, silent data corruption, a fail-safe stop or a hang; in PLANT, a trip and which mechanism made it; in ORBIT, how many errors the code corrected, or a restart and how the program ran after it. In PLANT and ORBIT the Protection panel shows the mechanisms cycle by cycle, from signals of the same run: the shadow core repeating the core two cycles later, the comparator's 308 bits, parity and the watchdog; or the three copies of the pc and the state with their vote, the words the code checks in this cycle, the scrubbers' positions and the restarts.

What this is

        The guardian (Phase 3) is a small, fixed piece of hardware beside the core, nexus4_guard in rtl/nexus4_core.vhd. It runs no software. It watches the core's commit port, keeps its own copy of a few variables of the program, and checks properties of them: invariants (linear comparisons such as cmd - pos <= 5), automata (which order of events is allowed) and deadlines (after one event, another within N cycles). The program tells it what happens with the marker instruction nx.mark. What it checks is not built into it: a property set becomes a table of 79 words, loaded with the program, so the same hardware checks any set. On the first violation it acts: in BASE and PLANT it trips and stops the system; in ORBIT (proposed, D59) it restarts the core with cause 4, and the program, which sees the cause, takes its safe branch.
        Everything below the property set comes from simulating the VHDL in this page: the guardian's own signals, cycle by cycle. The line under the timeline compares its verdict with the reference model, which CI compares with GHDL on every push.

How the drills are graded

        Each drill runs the plant's protection channel (tests/plant/channel.s) on the VHDL core of the Core page, in the profile the drill names. Nothing here stores an answer: when you run a drill, the kernel of the course simulates the core with the upset and without it, and the outcome is what the testbench reports, judged by the same function the Core page uses. CI runs every drill on each push (tools/drill-check.mjs): each prediction's outcome must be one of its choices, and each hunt must have a solution among the upsets the page offers.
        Predict: choose what the upset will do, then run it; right the first time scores 100. Hunt: the drill opens the Core page; try upsets there until one does what is asked; the first try scores 100, each further try 15 less, at least 25.

How the oracle works
differential testing

          

            
GHDL runs each example with --trace-signals. After every simulation cycle it prints every scalar signal with its value and two flags: A (active: a driver was updated) and E (event: the value changed). Composite signals appear as their scalar parts, for example m(1)(0) or r.n.

            
The NEXUS-4 kernel produces the same snapshots. The test tools load the kernel straight out of this file, with no build step, and any difference in a cycle, a value, a flag or a message fails the build. An example that uses a construct the kernel does not support yet is reported as pending; an example marked as required may never be pending.

            
One calibrated exception: for an assignment with a single zero-delay element that gives a signal the value its driver already has, with nothing else pending, the language standard still records a transaction. Nothing in the NEXUS-4 subset can observe it, so GHDL leaves it out. The kernel keeps it and tags it, because the difference between a transaction and an event is a lesson of the course, and the comparison leaves out exactly the tagged ones.

            
The tests are themselves tested: tools/mutations.mjs breaks the kernel in specific ways (inertial delay, resolution, rising_edge, delta counting and more), and every broken copy must fail.

            
VCD waveforms are only a secondary check: VCD merges the delta cycles of a time step, cannot hold arrays of vectors, and may reduce std_logic to four states.
